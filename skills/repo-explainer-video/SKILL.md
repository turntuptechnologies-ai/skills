# リポジトリ解説動画（repo-explainer-video）

## このスキルがやること

リポジトリを読み、種類に合った解説動画（MP4 + 字幕ファイル）を、目的・対象者・長さをユーザーと相談しながら作る。確認は「ヒアリング → 絵コンテ → プレビュー」の 3 点で取り、それ以外は止まらずに進める。

## 手順

1. **リポジトリを読んで種類を判定する。** README・エントリポイント・依存・ディレクトリ構成から決める。動画の内容は実装から裏を取る（実装に無い機能を見せない）。

   | 判定の手がかり | 種類 | 動画の形 |
   |---|---|---|
   | フロントエンド（React / Vue 等）、`dev` / `start` script、拡張機能・デスクトップアプリ | UI アプリ | 実際の UI を操作する録画 + 字幕 |
   | 論文 PDF・LaTeX（`.tex`）・実験コード・図表、README に論文リンク | 研究論文 | 発表スライド（問題 → 手法 → 結果 → 結論）+ 字幕 |
   | 上記以外（ライブラリ・CLI・API サーバー） | ライブラリ / CLI | スライド + コード断片 + 実行したターミナル出力 |

   - 複数に当てはまる（論文の実装に UI デモがある等）→ どちらを主にするかをヒアリングで聞く。
2. **ヒアリングする（確認点 1）。** 判定結果から既定値を埋めた表を示し、ユーザーには直すところだけ答えてもらう。

   | 項目 | 選択肢の例 | 既定値の決め方 |
   |---|---|---|
   | 目的・対象者 | 非技術者向け紹介 / 技術者向け解説 / マーケティング / 研究発表 | 種類から推定（研究論文→研究発表） |
   | 長さ | 30 秒 / 1〜2 分 / 3〜5 分 / 10 分 | 紹介・マーケ→1 分前後、解説・発表→3〜5 分 |
   | 言語 | 日本語 / 英語 | README の言語 |
   | ナレーション | 字幕のみ / 音声あり | 字幕のみ（音声は手順 5 で使える TTS を提示して選んでもらう） |
   | 縦横比・解像度 | 16:9 1920×1080 / 9:16 1080×1920（SNS 縦動画） | 16:9 |
   | 出力先 | 例: `video/`（作業ファイルは git 管理外） | リポジトリ外の作業ディレクトリ |

3. **絵コンテを作り、承認を得る（確認点 2）。** 下の形式で全シーンを書き、合計秒数を目標の長さに合わせる。字幕文の量は読む速さで決める（日本語 6〜8 文字/秒、英語 150〜170 語/分、1 シーン最低 2 秒）。対象者ごとの書き分け: 非技術者→用語を避けて「何ができるか・誰が嬉しいか」、技術者→構成・使い方・コード、マーケティング→課題と価値を先に示して最後に行動喚起、研究発表→主張と根拠（数値・図）。

   | # | 秒数 | 画面 | 字幕（ナレーション）文 | 素材 |
   |---|---|---|---|---|
   | 1 | 4 | タイトル | 〇〇を 1 分で紹介します | スライド |
   | 2 | 8 | ログイン後のダッシュボード | ここで△△を一覧できます | UI 録画: `/dashboard` |

4. **環境を確認する。** 書き出し前に不足を見つけ、入れるものは理由と容量を添えてユーザーに確認する（OS への変更や大きなダウンロードを伴うため）。
   - Playwright: `npx playwright --version`。UI 録画の章タイトル・操作ハイライト・字幕の重ね表示は screencast API（`page.screencast`、1.59 以降）を使う。1.59 より古ければ、操作ごとのスクリーンショットに切り替える。OS の共有ライブラリ不足は `npx playwright install-deps --dry-run chromium`（変更せずに判定。不足があれば一覧して非 0 で終わる）で確かめ、不足していれば `npx playwright install-deps chromium`（sudo が要る）か公式の Playwright Docker イメージを提案する。
   - ffmpeg: Playwright 同梱の ffmpeg は MP4（H.264）を出力できないので使わない。システムの `ffmpeg` が無ければ `uv run --with imageio-ffmpeg python -c "import imageio_ffmpeg; print(imageio_ffmpeg.get_ffmpeg_exe())"` でパスを得る。`<ffmpeg> -hide_banner -encoders` に `libx264` があることを確かめる。
   - 日本語フォント: ヘッドレス Chromium は日本語フォントが無いと文字が豆腐（□）になる。スライドは Web フォント（Noto Sans JP 等）を `@font-face` / `<link>` で読み込み、撮影前に `document.fonts.ready` を待つ。
5. **素材を作る。**
   - UI アプリ: README の手順でアプリを起動し、デモ用データで操作する。Playwright スクリプトで絵コンテどおりに操作して録画する。字幕は画面上に重ねる（screencast のオーバーレイ、またはスライドと同じ DOM 字幕）。
   - スライド: 1 シーン 1 枚の HTML（指定解像度・字幕領域つき）を Playwright で PNG に撮る。数式は KaTeX、コードは構文ハイライト、ターミナル出力は実際に実行した結果を使う（作った出力を見せない）。
   - ナレーションを選んだ場合: 使える TTS を下表から検出して提示し、ユーザーに選んでもらう。シーンごとに音声を合成し、その長さをシーンの秒数にする。

     | TTS | 確認方法 | 注意 |
     |---|---|---|
     | VOICEVOX（日本語） | エンジン（既定 50021 番ポート）が応答するか | 「VOICEVOX:キャラ名」のクレジット表記が必要。企業利用に事前確認が要る音声がある |
     | Kokoro（英語） | `python -c "import kokoro"` が通るか（未導入なら導入を提案） | 日本語は品質が落ちる |
     | クラウド API（OpenAI / Google 等） | API キーの環境変数 | 従量課金。費用の見込みを示してから使う。AI 音声である旨を明示する |

6. **プレビューを確認してもらう（確認点 3）。** シーンごとの静止画（UI 録画は代表フレーム）を並べて見せ、修正を反映する。全体を書き出してから直すより安い。
7. **書き出す。** シーンごとに長さを決めてクリップ化し、連結してから字幕を多重化する。静止画を concat の `duration` 指定で直接つなぐ方法は、長さがずれることがあるので使わない。
   ```bash
   <ffmpeg> -loop 1 -t <秒数> -i scene01.png -c:v libx264 -pix_fmt yuv420p -r 30 clip01.mp4   # 静止画シーン
   <ffmpeg> -f concat -safe 0 -i clips.txt -i subs.srt -map 0:v -map 1:s -c:v copy -c:s mov_text -movflags +faststart out.mp4
   ```
   - UI 録画（WebM）は同じ解像度・30fps の H.264 に変換してからクリップとして並べる。音声がある場合はシーンの音声を連結して多重化する（`-c:a aac`）。
   - 字幕は SRT と VTT を別ファイルで出す。画面に字幕を焼き込んだ場合は、上の `-i subs.srt -map 1:s -c:s mov_text` を外して埋め込み字幕を付けない（埋め込み字幕は既定で表示されるプレイヤーがあり、二重に出るため）。
   - 最後にエンドカードを付け、クレジット（TTS の表記・図版の出典・AI 音声の明示）を入れる。
8. **検証する。** `<ffmpeg> -hide_banner -i out.mp4` の `Duration` と解像度を確認し、`<ffmpeg> -ss <秒> -i out.mp4 -frames:v 1 check.png` で各シーンから 1 枚ずつ抜き出して目で見る（豆腐・字幕のはみ出し・秘密情報の映り込み・シーン切り替え位置のずれ）。問題があれば該当シーンを直して手順 7 からやり直す。

## ルール・コツ

- **秘密情報・個人情報を映さない。** `.env` の値・トークン・実ユーザーのデータが画面やターミナルに出ないよう、デモ用データと伏せ字を使う。動画は共有されて取り消せないため。
- **生成物をコミットしない。** 動画・中間ファイルは容量が大きいので git 管理外に置く。リポジトリに入れたいと言われたら Git LFS 等を提案する。
- **ライセンスを確かめる。** 論文の図版・他者のスクリーンショットは出典を入れ、転載の可否が不明なら作り直すかユーザーに確認する。Remotion は従業員 4 名以上の企業では有料ライセンスが要るので、既定では使わない。ffmpeg の静的バイナリは GPL なので、リポジトリに同梱・再配布しない。
- 確認点以外で止まらない。環境の不足を見つけたら、確認と同じメッセージで代替案を添える（例: 「Docker イメージで撮影するか、スライドだけで作るか」）。
- アプリが起動できない（環境変数・外部サービスが必要等）→ 推測で画面を作らず、起動できない理由を報告し、スライド中心の構成に切り替えるかを聞く。
- 長さの調整は字幕文を削って行う。シーンの秒数だけ縮めると字幕が読み切れなくなる。

## 完了条件

以下を全て満たしたら完了。**満たせない項目があれば、黙って省略せず理由を報告する。**

- [ ] 種類の判定結果と、ヒアリングで決まった項目（目的・対象者・長さ・言語・ナレーション・縦横比）を報告した
- [ ] 絵コンテをユーザーが承認し、プレビューをユーザーが確認した
- [ ] MP4（H.264・指定解像度）と字幕ファイル（SRT / VTT）を出力した
- [ ] `Duration` が目標の長さの ±10% 以内で、各シーンから抜き出したフレームに豆腐・はみ出し・秘密情報が無いことを確認した
- [ ] 画面とターミナル出力が実装・実行結果に基づいている（作った出力を見せていない）
- [ ] エンドカードと報告にクレジット（TTS・図版の出典・AI 音声の明示）を入れた（該当するもののみ）

## 報告フォーマット

```markdown
| 項目 | 内容 |
|---|---|
| 種類 / 目的・対象者 | UI アプリ / 非技術者向け紹介 |
| 長さ（目標 / 実測） | 60 秒 / 61.2 秒 |
| 解像度・言語・ナレーション | 1920×1080 / 日本語 / 字幕のみ |
| 出力 | `<出力先>/out.mp4`、`<出力先>/subs.srt`、`<出力先>/subs.vtt` |
| フレーム確認 | 8 シーン中 8 シーン OK |
| クレジット | なし（字幕のみ） |
```

## 補足

- 社名・内部 URL・認証情報などの固有情報は扱わない。
- README 自体を整えたい場合は `write-readme` を使う。
