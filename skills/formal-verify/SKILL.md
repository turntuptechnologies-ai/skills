# 形式検証（formal-verify）

## このスキルがやること

テストは思いついたケースだけを確かめる。モデル検査は、決めた範囲の全ケース（モデルの全実行順）を確かめる。プロパティベーステストは全入力ではなく、生成した多数の入力で確かめる（網羅ではないので、試行数と生成の範囲を報告する）。このスキルは、コードの約束を 1〜3 個の性質として書き、検証を作って走らせ、反例があれば実コードの言葉で報告する。合格の意味は「調べた範囲と前提の中で破れなかった」までで、システム全体の正しさではない。

## 手順

1. **対象を選ぶ。** 検証しやすい所ではなく、「破れると利用者が困るのに、テストではその場面にめったに届かない約束」を選ぶ（例: 並行する処理の排他、リトライと冪等性、状態遷移、件数や金額の上限、パーサーの冪等性）。約束は docstring・設計文書・コメント・既存テストから拾い、コードから分からないことだけユーザーに聞く。対象の指定があればそこから始める。
2. **既存のテストを読む。** その約束をどこまで確かめているかを把握する（自作の乱数テストが既にあることも多い）。同じことをする検証は作らない。
3. **性質を書く。** 1 つずつ「名前・常に成り立つべき内容・それを守っているコード（`path:line`）」で書く。
4. **道具を選ぶ。** 問いに答えられる一番安い道具を選び、選んだ理由を報告に書く。

   | 問い | 道具 | 例 |
   |---|---|---|
   | 実行順・タイミング（並行・リトライ・lease・状態遷移）で破れないか | モデル検査: 設計を小さな状態機械にし、全実行順をたどる | TLA+。使えない環境では、リポジトリと同じ言語で書いた明示的な状態探索（幅優先で全状態をたどり、違反までの最短手順を出す） |
   | 関数がどんな入力でも約束を守るか | 実コードへのプロパティベーステスト | Python は Hypothesis、TypeScript は fast-check |
   | 上限なしの全サイズで成り立つ必要があるか | 証明（Lean 等） | 手間が大きいので、必要性をユーザーに確認してから |

   - Java などの実行環境のインストールと、検査器のバイナリ（jar 等）のダウンロードは、ユーザーに確認してから行う（ユーザーの環境に入るため）。プロジェクトの依存に検証用ライブラリを追加する場合は、報告の変更点に書く。
   - TLA+ の検査器 TLC は、公式リリースの `tla2tools.jar`（Java 11 以降で動く）を使う: `gh release download <タグ> -R tlaplus/tlaplus -p tla2tools.jar -D <置き場所>`。リリースにチェックサムが無いので、実行前に jar のマニフェストの `X-Git-Revision`（`python3 -c "import zipfile; print(zipfile.ZipFile('tla2tools.jar').read('META-INF/MANIFEST.MF').decode())"`）が、公式のタグのコミット（`gh api repos/tlaplus/tlaplus/commits/<タグ> -q .sha`）と一致することを確かめる。ダウンロード・照合・実行は別々のコマンドで行う（取得したバイナリを確かめずに実行しないため）。
5. **検証を作る。**
   - モデル: 各動作に、対応するコードの `path:line` を注記する。1 つのトランザクション・1 つの不可分な操作は、モデルでも 1 つの動作にする。時刻・件数などの定数は縮めてよいが、順序関係（どちらが先に切れるか）は保つ。範囲（ワーカー数・時刻の上限・回数）と前提（例: DB の時計は戻らない）を、モデルのファイル冒頭に書く。
   - TLA+ で書く場合: 範囲・前提・壊した版の切り替えを `CONSTANTS` にし、条件ごとに `.cfg` を分ける。検査は `java -cp tla2tools.jar tlc2.TLC -deadlock -workers auto -config <条件>.cfg <仕様>.tla`。全ワーカーが終わった状態を行き詰まりとして誤報しないよう `-deadlock` で行き詰まりの検査を外す。終了コードは 0 が違反なし、12 が不変条件の違反（反例は出力の `State 1:` からの手順）。
   - プロパティベーステスト: 生成する入力は、実際に受理されうる形にする（チェックサムつきの ID などは、既存テストの作り方を使う）。「受理されたら〜」の形の性質だけだと、全部が拒否される壊れ方を見逃すので、「正しい入力は必ず受理される」性質も併せて書く。
6. **基準を走らせる。** 元のコードで全性質が成り立つか確かめる。失敗したら手順 8 で切り分ける。
7. **わざと壊して検出を確かめる。** 性質を守っている箇所そのものを壊した版で、検証が失敗することを確かめる。保険の層（今の依存の版では効いていない処理）を壊しても検出されないことがあるので、壊した版で検出されなければ、壊す箇所が約束を守っているかをまず疑う。
   - モデル: 壊したコードと同じ変更を、モデルの切り替え（例: `--mutant no-fence`）として入れる。
   - 実コード: 作業用のコピーか未コミットの変更として壊し、目印（例: `# SCRATCH`）を付ける。確かめたら元に戻し、目印が残っていないことと、基準が通ることを確かめる。
8. **失敗を切り分ける。** 反例の各手順が実コードで起こりうるかを、対応する `path:line` で確かめる。
   - 起こりえない（モデルの不可分性の誤り、不正なテストデータ等） → 検証の誤り。検証を直して手順 6 からやり直す。
   - 起こりうる → 発見。前提を 1 つずつ絞って再検査し、どの条件で起きるかを特定する（例: 時計が戻る量に上限を付けて、lease 期間未満なら起きないことを確かめる）。
9. **報告する。** 下の報告フォーマットで書く。

## 報告フォーマット

```markdown
## 検証した約束
| 性質 | 内容 | 守っているコード |
|---|---|---|
| I1 書き込みの排他 | lease を失ったワーカーの書き込みはコミットされない | `src/lease.py:120` |

## 道具と理由
<例: 実行順の問題なのでモデル検査。TLA+（TLC）で検査した>

## 範囲と前提
<例: ワーカー 2、時刻 0〜7、訪問は各 2 回。DB の時計は戻らない。プロパティベーステストは生成 3,000 件で、網羅ではない>

## 結果
| 条件 | 状態数 / 試行数 | 結果 |
|---|---|---|
| 基準 | 1,125,616 | 違反なし |
| 壊した版: 延長の条件から lease の値を外す | 922 | I1 違反を検出（7 手） |
| 前提を外す: 時計が lease 期間以上戻る | 22,322 | I1 違反（反例は下） |

## 発見
<反例を実コードの言葉の短い手順で。起きる条件と深刻度、取りうる対策>

## 実行方法
<コマンド。数分以内に終わること>

## カバーしない範囲
<モデルに入れていない処理・テストしていない入力>
```

## ルール・コツ

- **性質を緩めて合格させない。** 反例が出たら、それは発見として報告する。性質・モデル・範囲を変えるのは、手順 8 で検証の誤りと分かったときだけ。理由: 緩めた合格は、何も保証しない。
- プロダクトのコードは直さない。直すかどうかは発見を読んだユーザーが決める（壊して確かめる変更は元に戻す）。
- 反例は、モデルの変数名ではなくコードの言葉（関数名・列名・操作）で、短い手順として書く。
- 検証は数分以内で終わる大きさにする。状態数が爆発したら、範囲（ワーカー数・時刻の上限）を縮め、縮めたことを範囲に書く。
- 検証のファイルは、依頼があれば対象リポジトリに置く（例: `verification/<性質>/` に実行方法と、対応するコードの `path:line` を書いた README と一緒に）。コードが変わるとモデルは古くなるので、どのコミットのコードと照合したかも残す。

## 完了条件

以下を全て満たしたら完了。**満たせない項目があれば、黙って省略せず理由を報告する。**

- [ ] 性質ごとに、守っているコードの `path:line` を示した
- [ ] 既存のテストがその約束をどこまで確かめているかを報告した
- [ ] 元のコードで検証を走らせ、結果（状態数・試行数を含む）を報告した
- [ ] わざと壊した版で検証が失敗することを確かめ、壊した変更を元に戻して基準が通ることを確かめた
- [ ] 反例があれば、実コードで起こりうるかを切り分け、起こりうるものは起きる条件と共に発見として報告した
- [ ] 報告フォーマットの全節（約束・道具と理由・範囲と前提・結果・発見・実行方法・カバーしない範囲）を埋めた

## 補足

- 社名・内部 URL・認証情報などの固有情報は扱わない。
- 発見をユーザーが直すと決めたら、`create-issue` で起票し、`debug-root-cause` の手順で直す（反例の手順を再現手順・回帰テストに使う）。
